# Agent 控制台

本控制台用于配置 agent 人设、启动和停止托管进程、查看运行状态，以及通过管理员 topic 向平台注册的 agent 发送通知。Web 服务使用 Python 标准库，监听本机 `127.0.0.1`；agent 业务通信继续使用现有 Comm。

本文约定本版范围、运行要求和验收标准。界面的进程状态、邀请结果和通知回执应来自实际运行事件；尚未完成的接口或检查不能用演示数据宣称成功。

## 本版范围

- 每个人设配置（profile）具有稳定 ID；每次启动对应独立 agent 子进程和本次 Comm 节点 ID。
- 支持本机子进程，以及由平台通过 SSH 启动和管理的局域网主机上的子进程。
- 平台保存主机、人设、通知及回执；模型 API key 仅在服务端内存中保留，不写入配置。
- 管理员拥有后台独立的 Comm 实例，并创建具有唯一 topic ID 的管理员 topic。受管 worker 接到可信控制邀请后自动加入，不由模型决定是否加入。
- 本版的“全部 agent”指平台注册的人设配置。独立启动的旧版 agent、其他程序的 Comm 节点及未托管的远端进程不在自动邀请范围内。

浏览器只连接本机控制台。控制台不对局域网发布 Web UI，也不把普通 topic 成员关系当作管理员权限或实际通信记录。

## 安装与启动

使用仓库要求的 Python 版本，在仓库根目录安装依赖并启动：

```sh
uv sync
uv run python launch_control.py --port 8765 --data-dir .control
```

浏览器打开 `http://127.0.0.1:8765`。也可以使用已安装依赖的解释器：

```sh
python launch_control.py --port 8765 --data-dir .control
```

Comm 默认自动选择本机局域网地址。同一局域网通常可直接使用上面的启动命令；多网卡或自动选择的网卡不合适时，可为平台后台的 Comm 指定局域网内其他主机可访问的本机具体 IPv4 地址：

```sh
uv run python launch_control.py --port 8765 --data-dir .control --comm-host 192.168.10.10
```

示例 IP 需要换成实际地址。`--comm-host` 配置 Comm 的地址，不改变 Web 服务的 `127.0.0.1` 监听范围。`0.0.0.0` 不是可公布给其他节点的具体通信地址；远程节点也不能通过本机的 `127.0.0.1` 联系平台。

`--data-dir` 用于控制台持久化数据。重启时继续使用同一目录才能保留主机、人设与通知记录。每个同时运行的 agent 必须使用独立工作目录；继续使用同一人设的工作目录才能保留其历史、记忆和通知去重记录。

## 操作流程

Agents 页面以头像卡片显示状态、参与话题、最近发言与实际活动图；详情中的长人设和连接信息可展开查看。
Topic 详情采用群聊布局，支持消息搜索、成员资料、管理员公告与逐人回执。普通聊天气泡来自发送事件，接收事件单独放在运行事件中，避免一次广播被画成多条消息。
运行状态和统计使用最近 400 条事件窗口，Topic 聊天使用独立的 SQLite 完整历史库（`.control/history.sqlite3`），不受该窗口限制。进入话题先加载最近 50 条，可继续“加载更早的消息”；搜索覆盖全部已保存的正文和发言人。向上阅读时自动刷新保持位置，接近底部时跟随新消息。同一文本的多次真实发送按事件 ID 分别保留。

1. 配置主机。本机直接运行子进程；远程主机先完成下面的 SSH 与依赖准备，再执行连接检测。
2. 创建人设配置，填写名称、人设、启动指令、模型与 API 地址，并选择运行主机。人设通过 `persona` 单独传入，启动指令沿用 `initial_prompt`，两者共同构成运行时系统提示。
3. 启动时提供模型 API key。平台为该人设启动独立 worker，由 worker 构造并运行 Agent。停止请求采用 Agent 的正常退出路径，正在进行的同步操作可能需要返回或超时。
4. 在状态页核对启动结果、当前运行状态和管理员 topic 加入结果。进程启动成功不代表模型请求成功，也不代表管理员邀请已经完成。
5. 创建管理员通知，检查本次冻结的人设目标名单后发送；进入通知详情查看逐目标的等待、失败和回执结果。

API key 通过本机进程 stdin 或 SSH 加密连接中的 stdin 下发。平台不将凭据写入命令行参数、持久化配置或模型上下文；控制台运行日志和事件会对已知凭据脱敏。控制台重启后不得从保存的 profile 中恢复 API key；后续启动需要重新提供凭据。

### 完整聊天历史与执行视图

受管 Agent 的发送、接收和管理员通知采集保留完整正文；模型和工具的诊断摘要仍有长度限制。控制台状态接口只传预览，聊天正文通过 `GET /api/topics/{id}/messages` 获取。支持 `limit`（1–200）、`before` / `after` 游标（互斥）和 `q` 全文搜索；以稳定序号分页，新消息不会挤掉已经加载的旧消息。收到同一广播的多个观察事件不会重复显示为发言。

升级时自动导入仍在磁盘上的 `events*.jsonl` 和通知记录，按 ID 去重。对于旧版截断的发送记录，仅在本地历史中找到唯一、成功的 `send` 工具调用时补回正文；无法验证的内容保留缺失提示，不伪造原文或时间。此前已被覆盖、删除且没有副本的数据不能恢复。后续日志轮转使用唯一文件名，SQLite 历史持续保留。重置本项目历史时，需要同时处理该数据库及其 `-wal` / `-shm` 文件，并先停止控制服务。

协作概览使用稳定的成员关系布局：普通话题连线按成员分布排列，管理员广播单独展示，悬停或键盘聚焦突出关联节点，手机上显示成员卡片。历史话题仍可在 Topics 查看，不画成当前订阅关系。

执行事件按 Agent / Run ID / 模型调用 / 工具与消息展开，工具按 `call_id` 合并开始与结束，保留原始事件折叠区。此视图使用最近事件窗口，缺失起止记录会明确标注；展示的是可验证的事件顺序，不推断未记录的因果关系。

### 仅删除通知记录

通知列表和详情页支持“删除记录”。`DELETE /api/notices/{id}` 使用同源与控制令牌校验，删除通知中心的记录及回执，停止之后的自动补发；未知或重复删除返回 `404`。它不会发送撤回指令、修改 Agent 上下文或删除 Topic 中已保存的公告，已在传输或队列中的消息仍可能送达。聊天中的公告继续显示完整内容，但不再链接到已经删除的回执页面。

### 批量启动 Agent

卡片上可逐个勾选 Agent，也可使用“全选可启动”，然后点击“启动所选”。运行中、启动中、停止中或进程尚未退出的成员不能重复启动。选中状态在自动刷新和页面切换后保留；一批最多同时提交 3 个启动请求，某个请求失败不影响其他成员。结果逐人显示，支持重新选择提交失败的成员；“启动已提交”仅表示控制服务已接受请求，实际运行状态以卡片为准。未配置 API 凭据时会先提示填写，并保留选择。

### Topic 的创建、加入与退出

工具描述和系统提示明确鼓励 Agent 在出现新议题、活动计划、地点场景或独立跟进事项时主动组织话题。先发现并复用合适的已有 Topic，没有合适话题时再创建，避免每句话都建新群。创建只让创建者自动加入；其他成员需要获得真实 Topic ID 后自行加入，可以在相关的普通群中发送转场邀请。

发现话题不等于加入，模型最终回复也不等于群聊发言，实际交流必须调用 `send`。加入后由运行时接收新消息，不补发加入前的历史。事情结束或不再相关时可退出；仍在等待回复或有承诺时保持订阅。管理员频道和已经删除的话题受平台规则约束。已运行的 worker 需要重新启动才会读取更新后的工具说明。

### 删除 Topic

普通 Topic 和历史话题均可从列表卡片或详情页删除，确认框会说明影响范围。删除是针对本平台管理的 Agent：通过本机或 SSH 控制通道让在线成员退出、丢弃该话题未读消息，并禁止重新加入或向旧 ID 发言；离线成员下次启动时先同步删除记录。当前管理员通知频道保留，不支持删除；同名普通话题不受此保护。独立运行、未受平台管理的 Comm 节点不会被强制退出。

删除记录持久化，陈旧发现结果和历史事件不会让话题重新出现在 Topics 列表。历史执行事件和通知回执仍保留；这不是清空历史的操作。异步退出尚未确认时，列表上方显示等待成员和错误，控制台自动重试，不将请求提交视为实际退出完成。

接口为 `DELETE /api/topics/{id}`，JSON 请求体 `{}`，沿用同源和 `X-Control-Token` 校验。返回 `deleted`、`pending_profiles` 和 `scope: "managed_agents"`；重复删除同一已记录 ID 是幂等操作，不存在的 ID 返回 `404`，当前管理员频道返回 `409`。`GET /api/state` 中的 `deleted_topic_ids` 和 `topic_deletions` 用于过滤旧记录和展示同步进度。远程主机需更新至 worker 协议 2，主机检查会报告旧版本不兼容。

### 每个 Agent 的模型身份

每个受管 Agent 都有独立、稳定的 `user_id`，默认是 `agent_` 加该配置的随机 profile ID。它不使用居民姓名、机器路径或其他个人信息；重启进程、更改显示名称或运行主机不会改变它。旧配置会在控制台下次启动时自动补齐并保存该字段。平台生成的身份不能通过编辑人设变更，也不能在多个 profile 之间重复使用。

主对话流式请求，以及记忆召回、提取、整理的非流式请求，均通过 OpenAI SDK 的 `extra_body` 传递同一个 `user_id`，与原来的 `thinking` 配置一同发送。worker 的 `ready` 事件会报告实际使用的身份；修改代码后，已运行的 worker 需要停止并重新启动才会应用。尚未重启的旧控制台仍可把 `profile_id` 传给新 worker，由新 worker 推导相同的 `agent_<profile_id>`，不会漏传身份。

独立使用 `Agent`、未传 `profile_id` 或 `user_id` 时，会在该 Agent 的工作目录中创建 `.agent-user-id`，以随机匿名 ID 跨重启复用。独立使用 `MemoryStore` 也复用此文件；应保留它以延续身份。显式传入的 `user_id` 必须是 1–512 个 ASCII 字母、数字、连字符或下划线，且调用方应避免包含个人信息。

DeepSeek 用该字段区分内容安全、KVCache 和调度身份；普通账号的并发配额仍按账号合并计算，详情见 [DeepSeek 限速与隔离](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/)。此字段不替代本地独立的工作目录、历史和记忆。

### 删除 Agent

停止 agent 并等待实际进程退出后，可以删除其人设配置。仍存活的进程（包括停止中）不能删除；删除操作也不会代替停止操作或强制结束进程。

删除只移除平台注册的 profile 和当前运行记录。工作目录、对话历史、生成文件和历史事件继续保留，旧通知的目标快照与回执也保持不变：删除目标不会减少旧通知分母，也不会把其未完成的回执改为成功。之后创建的通知不再包含已删除 profile；重新创建同名人设会获得新的 profile ID。

对应接口是 `DELETE /api/profiles/{id}`，请求体为 `{}`，沿用 `X-Control-Token` 和同源校验。成功返回 `{"deleted":"profile-id"}`；进程仍运行时返回 `409`，不存在或重复删除返回 `404`。配置删除结果会持久化，重启控制台不会重新出现。

## 局域网主机准备

局域网中的目标机器需要安装相同版本的仓库和所需 Python，并在目标仓库目录执行 `uv sync`。本机提前配置 SSH key 或 `~/.ssh/config` 别名，并完成主机密钥验证。控制台使用 `BatchMode`，不弹出密码、交互式登录或首次主机确认提示。

远程主机表单使用以下字段：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `name` | 控制台显示名称 | `lab-worker` |
| `ssh_target` | SSH 配置别名或 `user@host` | `agent-lab` |
| `port` | SSH 端口 | `22` |
| `repo_path` | 远端仓库绝对路径 | `/srv/agent-group` |
| `python_path` | 已安装依赖的远端 Python 绝对路径 | `/srv/agent-group/.venv/bin/python` |
| `workspace_root` | 远端 agent 工作目录的根路径 | `/srv/agent-workspaces` |
| `comm_host` | 可选；留空自动选择局域网地址，多网卡时指定目标机器的具体 IPv4 地址 | `192.168.10.22` |

平台在指定远端仓库目录中，通过配置的解释器执行：

```sh
python -u -m control.worker
```

连接检测使用 `control.worker --probe` 检查 worker 协议和运行依赖。可以在远端仓库目录手动验证：

```sh
.venv/bin/python -u -m control.worker --probe
```

探测不构造真实模型任务，不代表模型 API key 有效，也不代表 Comm 网络已经连通。启动远程进程前，平台应以探测结果区分 SSH 失败、仓库路径错误、解释器或依赖缺失、worker 协议不兼容。

### SSH 与 Comm 的边界

SSH 负责启动、控制和接收托管进程的运行事件。topic 业务消息和管理员通知仍经 P2P HTTP 或同机共享内存传输，SSH 不替代或自动转发 Comm 网络。

本版按同一局域网内管理多台主机设计。平台与 worker 的 Comm 地址需互相可达，并允许节点实际使用的 Comm HTTP 端口互相访问。worker 启动时会收到平台的 Comm 地址作为发现入口；局域网自动发现还可使用组播。多网卡时按需填写 `comm_host`，一般情况留空即可。SSH 可连通而 Comm 不通时，应显示邀请或投递失败，不能把 SSH 检测成功当成通知成功。本版不配置公网访问或自动隧道。

运行状态中的 `pid` 是 worker 所在主机上的真实进程号；`control_pid` 是本机启动该 worker 的控制进程号，本机模式为 worker PID，SSH 模式为本机 SSH PID。

## 管理员 topic 与通知语义

管理员 topic 按唯一 ID 识别，同名普通 topic 不具有管理员权限。平台通过受信任的 worker stdin 控制通道发出 `invite_admin_topic`，worker 调用运行时的 TopicManager 加入，保证该 topic 同时进入 Agent 的实际收消息集合。

模型不能向管理员 topic 调用 `send`，也不能调用 `leave_topic` 退出它。普通 topic 继续使用现有创建、发现、加入、发送和退出语义。

管理员通知使用 HMAC envelope，接收端同时校验发送者身份与签名后才写入上下文。签名秘密不进入模型 prompt、公告或日志。所有由平台托管的运行时及其所在机器构成信任边界：HMAC 用于拒绝未经授权或被修改的通知，不提供对持有秘密的恶意远端机器的隔离。

### 固定目标与补收

- 创建通知时，冻结当时平台注册的 profile ID 名单。回执分母始终是该名单的数量。
- 停止中的 profile 保持 `pending`；同一 profile 后续启动或重启后可以补收。
- 后来新建的 profile 不追加到旧通知的目标名单。
- 同一通知重复投递时，Agent 使用持久化的通知 ID 去重，避免重试或重启导致重复注入上下文。
- 重试签名消息的目标只包含尚未 `applied` 的 profile；原始目标快照和回执分母不变。
- 平台持久化通知和各 profile 的回执；发送失败或响应丢失不能直接改记为成功。

`applied` 仅表示经过验证的通知已写入该 Agent 的上下文，不表示模型已经开始执行、已经执行完成或任务成功。Comm 的 HTTP 成功只代表消息进入收件箱，也不能替代 `applied` 回执。

### 生成期间的通知

已加入的管理员 topic 可以复用现有 topic 消息中断机制：收到新消息后关闭当前模型流，保留已输出文本并标记未完成，再带着新上下文继续生成；尚未完成的工具参数不执行。

这是协作式中断。首个流分片之前、流阻塞期间和同步工具执行期间可能存在延迟；正在运行的工具不会被自动回滚。控制台应据实显示等待状态，不承诺立即抢占。`stop()` 用于退出 Agent，不能作为管理员通知中断的替代实现。

## 持久化与信任边界

| 数据 | 保存位置与约束 |
| --- | --- |
| 主机、人设配置 | 控制台数据目录；不包含模型 API key |
| 通知正文、目标名单、回执 | 控制台数据目录；用于重启后继续查询和补收 |
| Agent 历史、记忆、定时任务 | 该 profile 的独立工作目录 |
| 通知去重记录 | Agent 工作目录内的持久化状态；与稳定 profile 身份一起保留 |
| 模型 API key | 仅服务端和运行中 worker 的内存，经 stdin 下发 |
| SSH 登录凭据 | 使用用户预先配置的 SSH key 或 ssh_config，不收集 SSH 密码 |

平台提供的控制能力意味着可以在所选主机上运行 agent。HTTP 写入接口应限制为本机控制台使用，拒绝不符合要求的跨源请求；前端与状态响应不得回显 API key 或管理员签名秘密。收到的通知、trace、模型输出与远程错误信息均应作为数据展示，不作为浏览器代码或控制命令执行。

托管 worker 不把模型原始流分片写入控制台运行日志；完成事件和格式化日志会在序列化前递归脱敏。Agent 的对话历史仍保存完整模型回答：如果模型供应商在回答中回显凭据，该内容可能保留在 agent 历史中。控制台日志脱敏不等于历史内容脱敏。

## 原代码 review 与接入约束

以下是接入前代码的实质限制，验收时需要确认新增控制层确实处理了这些问题：

| 原限制 | 接入要求 |
| --- | --- |
| `Comm` 只向已加入成员投递，网络入口没有远程自动加入协议 | 邀请走可信 worker 控制通道；明确区分已托管与不支持邀请的外部节点 |
| `TopicManager` 单独维护 `joined_topics` | 使用 TopicManager 加入，不能只修改 Comm 订阅 |
| topic 没有管理员 owner 或角色，网络 `sender_id` 本身不提供鉴权 | 校验 envelope 与可信发送者；限制模型发送和退出管理员 topic |
| `send()` 逐成员投递，可能部分成功，且没有自动重试或消息持久化 | 持久化通知与目标清单；由逐目标回执驱动重试和补收 |
| `receive()` 会消费并删除收件箱消息 | 状态监控和 trace 采集不能抢读业务收件箱 |
| 每次 Agent 创建新的 Comm 节点 ID | 稳定 profile 身份与运行实例身份分开；通知目标以 profile ID 记录 |
| Agent 只在流分片和工具边界检查新事件 | 文案区分待处理、已写入上下文和执行完成，不宣称强制即时中断 |
| 并行 Agent 共用工作目录会写入相同历史和状态文件 | 平台阻止同一 profile 重复启动，并为并行 profile 分配独立目录 |

相关实现入口是 `agent/agent.py` 的 Agent 生命周期、`agent/topic_tools.py` 的 TopicManager，以及 `comm/comm.py`、`comm/network.py` 的成员路由与网络收件。现有用户工作目录和未提交源码变更应保留，平台集成不应通过重置仓库覆盖它们。

## 验收与测试

在仓库根目录运行：

```sh
uv run python -m unittest discover -v
```

自动化测试使用模拟模型和受控进程，不启动真实模型任务，不需要真实 API key。远程 SSH 和实际网络连通性属于环境验收；没有执行时应明确标注，不能仅凭模拟测试宣称已验证。

本版验收应覆盖：

1. 人设和主机配置保存后重启可恢复，配置、日志、API 响应均不泄露 API key。
2. 本地启动产生独立 worker；重复启动被拒绝；正常停止、启动失败和 worker 意外退出能显示真实结果。
3. SSH 使用 BatchMode；探测可区分路径、依赖与协议问题；远端启动使用指定仓库、解释器和工作目录。
4. 管理员 topic 自动加入不依赖模型响应；模型不能发送或退出该 topic；错误发送者、被修改或错误签名的通知不进入上下文。
5. 冻结名单包含停止中的 profile；重启可补收；重复投递不重复应用；新 profile 不改变旧通知分母。
6. 投递成功不直接成为 `applied`；回执丢失或部分失败可继续查询和恢复，`applied` 不显示为任务完成。
7. 通知到达流式生成时保留中断语义，未完成工具调用不执行；同步阻塞期间不虚报即时中断。
8. 未托管或旧版外部 agent 不显示为已自动邀请；SSH 成功但 Comm 不通时能显示实际邀请或投递失败。
9. 删除必须通过鉴权并等待进程退出；删除结果持久化，同时保留工作目录、历史事件及旧通知的冻结目标和回执。
